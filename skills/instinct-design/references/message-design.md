# Message design

Put the part that changes the user's decision at the beginning. Imagine the message is truncated after its opening. The user must still understand the actual result and any decisive limitation.

## Choose the message by its job

| Situation | Opening | Necessary follow-up |
| --- | --- | --- |
| Verified completion | What is done and where to use it | Evidence or receipt when useful |
| Recommendation | The recommended choice and why it matters | Main tradeoff and uncertainty |
| A decision is needed | The exact decision and consequence | Prepared result, alternatives if material |
| Partial success or failure | What remains incomplete | Retained work and the next recovery action |
| Time-sensitive update | What changes and the deadline | The action that prevents loss |
| Nothing requires action | Usually no message | Digest or task history if requested |

Do not force all messages into one template. A one-line confirmation can be enough. A consequential choice needs more detail.

## Write the opening

Use concrete nouns and active verbs. Match the user's language and level of expertise. Lead with the answer rather than a greeting, an introduction, or a description of the process. Technical labels are useful only when the user needs them.

Name uncertainty in the same sentence or immediate next line when it changes what the user can do. "The invitation is sent; Alex has not accepted yet" is more useful than "The meeting is scheduled."

Don't prescribe a universal character count. Notification previews, tables, screen readers, and detailed reports have different constraints. Keep the opening short enough for its real context, then check it on that context.

## Give detail a clear home

Use labels that tell the user what expansion provides, such as "View price breakdown", "Why this option", or "Check delivery status". Avoid vague "More" labels when several details are available.

For comparison tables, documents, or editing, provide an artifact with a short message that says what it contains and its status. Keep costs, external consequences, and blocking unknowns above the disclosure.

## Examples

**A file is ready.** "The comparison is ready. Supplier B has the shortest quoted lead time; freight is still unconfirmed." Expand the table and quote sources when requested.

**Preparation is complete.** "The booking form is ready. Submitting it costs $120 and the venue does not offer refunds." Present the exact submission action if it requires a new decision. Do not claim a reservation exists.

**An action failed.** "The upload failed, so your post is not published. Your draft is saved. Retry the upload." Keep the diagnostic error in an expanded view.

**A suggestion conflicts with scope.** "The available ticket exceeds your $300 limit. I found a $340 option; no ticket has been bought." Ask only about the material price change, preserving the original search.

These are synthetic examples, not observed Instinct responses or proof of product behavior.
